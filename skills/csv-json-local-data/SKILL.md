# Android 文件与序列化数据

## 从真实数据契约开始

读取数据入口、CSV header、带引号的样例、JSON 模型与消费方。先写清编码、必填字段、日期格式、空值、关联 ID 和冲突策略。区分 assets、系统文件 picker、URI 或网络响应；外部文件沿用系统授权，不硬编码设备路径。

确认文件是持续读取的数据源、一次导入还是导出结果。已有 Room 等权威数据源时，不擅自恢复成运行时 CSV + JSON 双来源。新项目先按需求选存储；旧 JSON 恢复和导出不等于已获准迁移整个数据层。

## CSV 的决策与修复

1. 优先使用项目已有且适配当前方言的解析器。新实现有跨行引号字段时，选择支持记录级解析的成熟方案；不用 `split(",")` 或逐行读取冒充完整 CSV 支持。
2. 在单一入口处理 header 的 BOM、首尾空格和大小写。别名必须显式映射，例如 `itemid` 与 `item_id` 不是同一个字符串。导出内容按相同方言转义；面向电子表格时按需求防止公式文本被执行。
3. 先验证必填列再映射行。BOM/大小写规范化后出现重复列或别名冲突时，不让 map 静默覆盖；缺关键关联 ID 的记录按明确策略拒绝或跳过，可选缺列才回退。
4. 为保留既有单行解析器做小修复时，核对引号内逗号、`""`、尾部空字段及未闭合引号。数据允许字段内换行时，单行修补不足以满足契约。
5. 区分“成功但没有记录”“个别记录被拒绝”和“整个数据源失败”。复用现有结果接口；若当前接口只能返回空列表，如实报告限制，不宣称已区分失败状态。

缺少记录 ID 时，不默认拿行号当持久身份。先确认导入规则；文件改序后不稳定的 ID 不适合关联用户数据。

## JSON 列表存储

复用项目已有 Gson、kotlinx.serialization 或其它序列化方案；Gson 读取泛型列表时需要带元素类型的 TypeToken。解析出对象后仍按业务契约检查必要字段，不把 JSON 可解析等同业务记录有效。

只有项目确实使用 preferences 列表时才做其读-改-写修复：先读后写，保留既有 key、模型字段和其它用户记录；文件/数据库写入沿各自原子性契约处理。

| 存储状态 | 处理原则 |
| --- | --- |
| key 不存在 | 可按既有首次使用契约返回空列表 |
| 合法空列表 | 正常空数据，不等于读取失败 |
| JSON null / 损坏 JSON / 类型或元素不匹配 | 与缺 key 分开判断，显式失败或按已定义策略恢复；不要直接覆盖原值 |
| 两用户共用一份列表 | 写入保留全量记录，展示按当前关联 ID 过滤 |

坏 JSON 时不要用“默认空列表 -> 追加新对象 -> 保存”静默擦掉旧数据。按已有授权和恢复策略处理，不在日志中打印密码或完整个人记录。

`apply()` 的内存更新和异步写磁盘不等于事务提交；一次读-改-写也不提供并发追加保障。重复写入时先确认是按钮重复触发、业务重试还是并发写入，再决定按稳定记录 ID 去重、串行化或存储迁移。仅在单个 helper 内加锁不能保护其它实例或进程。

## 验证与结果

- CSV：列顺序变化、header aliases、引号内逗号、转义引号、尾空字段、关键缺列和坏记录；跨行支持按数据契约测。
- JSON：缺 key、空列表、正常往返、损坏内容保留、A/B 用户追加互不覆盖；磁盘读取用重启验证，不能只看当前内存。
- 两来源合并：先明确重复身份的处理规则；简单拼接既不等于去重，也不自动排序。

交付说明字段映射、拒绝/恢复策略、已验证路径及存储边界。认证优先级和导航留在对应业务层，不在解析器中决定。
