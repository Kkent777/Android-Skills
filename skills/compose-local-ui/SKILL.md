# Android Compose 界面与状态

## 先确定状态的主人

读取目标页面、模型、导航回调、状态持有者及现有 Material 依赖。新页面遵循项目设计系统；现有页面只沿当前需求的数据流追踪。已有 ViewModel、repository 或回调模式继续复用，已有 Compose 页面不为表单小改动切换 UI 框架。

将状态按寿命区分，避免“画面恢复了”被误认为“业务记录已保存”：

| 状态 | 决策 |
| --- | --- |
| 菜单展开、未确认的 picker 选择 | 页面内临时状态；取消不覆盖表单值 |
| 输入内容、已确认的日期时间 | 由已有状态持有者管理；页面局部值需恢复时用 rememberSaveable，复杂对象复用既有 Saver |
| 列表数据和加载结果 | 由已有加载层提供；Flow/StateFlow 通过项目已有的生命周期感知方式收集 |
| 重启后仍需存在的勾选或记录 | 存储需求；`remember` / `rememberSaveable` 都不是持久化方案 |

用户相关状态的 key/作用域要随用户 ID 变化；不可让用户 B 继承用户 A 的草稿或勾选。业务若允许跨用户草稿，按既有明确契约处理。

## 实施流程

1. 先列出字段、校验规则、错误显示和成功事件。规则以目标产品为准，商品数量、任务标题或备注上限等示例不能直接移植成所有应用的要求。
2. 保持单一可信状态源。输入通过 `value` / `onValueChange` 更新；更改字段只清除相关错误，不抹掉其它字段的失败提示。
3. 对日期时间分别保存“已确认值”和“对话框草稿”。确认提交草稿，取消保留旧值；Clear 同时处理下次打开 picker 时的初始值。
4. 提交时集中校验，捕获当次表单值和身份，再执行写入。保存期间阻止重复提交；失败保留输入并允许重试。已有异步事件处理不要在重组时反复消费同一个成功标志。
5. 页面通过已有 `onSaveSuccess` / `onBackClick` 等事件表达跳转。成功提示、清空和返回在保存成功后发生；响应式查询应随写入更新，一次性查询才需要显式刷新，避免叠加两套刷新状态。
6. 不在 composable 函数体直接启动重复读取/写入。读取复用已有加载机制；需要 effect 时明确 key，避免每次重组或多次提交重复执行。

长表单检查键盘弹出后的按钮可达性；列表项使用记录身份而非可变位置关联勾选。不要为小修复引入新的架构或更换组件库。

异步保存期间允许离开或切换用户时，晚到的成功事件不得清空新草稿或跳转新用户页面；按既有请求 ID/会话作用域丢弃过期 UI 结果，写入本身是否撤销以产品契约为准。Material DatePicker 的所选毫秒代表 UTC 日期起点；只保存日期时按 UTC 提取日历日，不先转设备时区；只有具体时刻才按明确时区转换。

## 按改动验证

- 表单：空白、非法值、修正单字段、保存失败、保存成功和重复点击。
- picker：确认、取消、Clear 后重开，已选日期与显示文本保持一致。
- 状态：重组、旋转、退出再进入、用户切换；区分可保存 UI 状态和真实磁盘记录。
- 列表：保存后返回刷新、空数据和加载失败的区别、勾选项与计数一致。

行为测试沿已有语义与事件验证，截图另查布局、字体和主题；性能疑问先用可比构建和帧/trace 证据定位。不要把减少重组次数或更新截图基线直接当功能/性能修复成功。

输出说明实际修改的状态归属、已跑检查和未验证路径。仅界面校验或提示成功，不代表业务数据已经保存。
