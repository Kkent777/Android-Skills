# Android 测试策略与回归

## 从工程和风险开始

读取目标模块/变体、Gradle/version catalog、test/androidTest、runner、CI 和现有测试。辨认 Compose、Views 或混合 UI，已有 JUnit、测试调度器、fake/mock、数据库、截图和设备环境；依赖存在不等于已有可运行测试。

列出本次会改变的行为、最可能回归的合同与需要真实平台才能确认的路径。复用现有框架和注入方式；没有 DI 框架不等于要安装 Hilt，没有截图需求也不默认增加截图插件。

## 按行为选择测试层

| 要验证的行为 | 适合的证据 |
| --- | --- |
| 纯计算、校验、映射、状态转换 | JVM 单元测试；断言输入与可观察输出 |
| 异步加载、取消、过期响应、重试 | ViewModel/业务层测试，使用现有可控调度器与数据替身 |
| SQL、外键、查询范围、事务与迁移 | 相应 Room/SQLite 测试；升级用旧 schema/数据库验证保数据 |
| 点击、表单、导航、恢复与错误反馈 | Compose/Espresso 等现有行为测试，按配置选择宿主或设备 |
| 文字溢出、布局、主题与字体变化 | 截图/布局检查；不能替代交互断言 |
| 系统权限、通知、后台、外部 Activity、硬件 | 支持该能力的模拟器/真机测试，明确设备与系统条件 |

Robolectric 只在项目配置与目标行为适合时使用，不把所有 androidTest 搬成宿主测试。无设备时如实报告平台路径缺证据。

## 让失败可定位

1. 为回归先构造最小失败输入，再修改实现；纯低风险文案无需人为制造复杂测试。
2. 优先沿现有替换点使用 fake；确需 mock 时采用已用库，不为一项测试重构整套数据层。替身也要覆盖真实契约的错误、空值、取消和返回顺序。
3. coroutine 测试使用项目支持的测试调度器控制时间与执行顺序。通过事件、状态或同步机制等待，不用固定 sleep 掩盖竞态；收集 Flow 的任务要能结束或随测试取消。
4. 用可控 clock、固定 fixture 和确定的记录身份覆盖跨日、排序与重试，不依赖测试当天日期和真实网络。
5. 数据库空库测试不证明磁盘重启或版本升级正确；内存 fake 也不证明实际 SQL 引擎行为。
6. UI 优先匹配用户可感知语义或既有 View 标识，必要时才加稳定 tag。验证动作后的业务结果，不只断言按钮存在或显示“保存成功”。

## 配置、截图与设备边界

核对 AGP、插件和库的实际兼容性再配置测试任务；不为获得某个截图 API 自动升级整个工程。确认源集、runner、变体、任务和输出路径真实存在。

布局样本按产品支持的窗口、字体、主题与语言选择，不把固定尺寸矩阵当全部应用标准。基线必须人工确认，截图差异不能通过全量接受新基线直接抹平。

关键用户链路至少覆盖正常操作与相关失败恢复：空数据、写入失败、取消/晚响应、返回、账号/工作区切换。没有账号的应用不加认证测试，业务未支持的状态不写成实现要求。

## 执行与报告

先运行与改动相关的测试，再按风险补编译、Lint、目标变体打包和平台验证。发现失败先保留错误、任务、变体和输入，区分实现回归、fixture 不符、环境缺失与偶发不稳定，不盲目重试到绿。

报告测试命令、运行环境、通过/失败/跳过数量与未覆盖路径；无任务或无设备不是通过。覆盖率可辅助定位缺口，但不是质量或功能正确性的证明。

需要规划具体回归时读取 [测试选择与验收场景](references/regression-selection.md)。
