# Room 导入、迁移与同步场景

以下为通用设计示例，表名与版本不是规定值，也不是已经运行通过的迁移。

## 本地任务应用

Task 可能关联 Project，也可能只有一个无账号任务列表。先读真实模型决定是否需要 userId、projectId 或外键，不为使用 Room 自动增加多账号架构。

任务列表通过单次查询加 refresh 或 Flow 订阅驱动 UI，二者选用现有机制。StateFlow 不会把单次 SQL 查询自动变成持续观察。

## 初始目录导入

- 只有产品需要预装目录时才做 seeding，无初始数据的应用不需要 CSV 或 db_seeded。
- 父子记录在 transaction 中按依赖顺序导入，解析失败不能当空数据设置完成标志。
- Room 提交成功与 preferences flag 落盘不是同一原子操作；重试策略必须避免覆盖用户编辑或 REPLACE 级联删除。
- 需要改进时可选择库内导入标记或幂等导入，按现有版本与约束决定，不强制增加新表。

## schema 升级

假设给 Task 新增非空字段：迁移需为旧记录提供可接受值，SQL schema 与 entity 期望相符，并在数据库 builder 注册路径。只添加 @Ignore 属性或改显示函数不等于数据库 schema 改变。

用旧库数据升级验证记录数量、字段、关联与索引；还要检查新装空库。新版本 Kotlin 编译通过不证明迁移正确。

## 每日打卡

保存完成值与日期，按产品时区判定今天是否有效。只存最后一天状态不构成历史日志；要统计连续天数时需合适的历史模型，不能从单个布尔值推算。

跨天重新读取与前台午夜刷新是不同需求，后者要有日期变化或恢复前台的重算触发。

## 联网缓存与离线编辑

区分本地 ID、远端 ID、待同步编辑和缓存失效；不要把已写 Room 当作服务端已提交。解决冲突时保留版本或服务端协议需要的信息，后台重试不重复创建同一记录。

迁移、存储故障与同步协议分别验证，不用卸载/清数据掩盖升级失败。
