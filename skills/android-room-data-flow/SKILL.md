# Room 数据流与持久状态

## 先确认数据契约

沿页面事件 -> 状态/业务层 -> Repository -> DAO -> Room 追踪当前功能，读取 entity、DAO、数据库版本、迁移注册及启动入口。复用已有 MVVM/MVI 或分层模式，小改动不引入新的依赖注入框架。

先列出表、主键、外键、实际作用域字段、时间表示和冲突策略。已确定 Room 是结构化数据唯一来源时，CSV 用于导入/导出，preferences 承载项目约定的轻量配置或 session，不恢复屏幕运行时 CSV/JSON 合并查询。

## 首次导入：需要初始数据时再应用

1. 启动时先完成导入检查，再允许依赖种子身份的会话恢复与页面查询；加载、成功和失败应可区分，不能失败后仍进入“初始化成功”的界面。
2. 文件读取与解析安排在合适的 IO 上下文。先验证必要列、记录 ID、父子关联和数量；读取器吞错后返回空列表，不能直接当作合法空数据并写入完成标志。
3. 在 Room transaction 中按外键顺序插入父表和子表，成功后才设置完成标志。mutex 只能约束共享同一把锁的调用者，不能代替数据库事务或跨进程保障。
4. 专门处理“Room 已提交，preferences 标志尚未落盘就退出”的重试窗口。按项目契约选择数据库内完成标记，或验证过的幂等导入策略；已有 flag 不必为此无条件新增表。
5. 重跑导入不得覆盖用户编辑、删除新增记录或意外触发外键级联。检查冲突策略；SQLite REPLACE 可能先删除旧行再插入，不能当作普通无损更新。忽略冲突也需验证最终父子数据完整性。

## 迁移：版本、SQL、注册和数据一起核对

- 数据库 schema 改变时同步增加版本并注册完整迁移路径，核对列名、类型、非空、默认值、索引和外键与 Room 期望一致；仅修改非持久化属性不自动要求迁移。
- 区分旧库升级与空库新建。新增非空列要能填充旧记录，迁移 SQL 的默认值需与 entity/schema 契约匹配。
- 保留现有记录与身份关联；未经任务明确许可，不用 destructive migration、卸载或清数据代替修复。
- 优先使用已有导出 schema 与迁移测试；有历史 schema 时验证逐级升级和历史数据，不以新库编译通过代替迁移成功。

## ViewModel 状态与真实写入

DAO 的 suspend 单次查询与 Flow 持续观察是两种机制。StateFlow 只是 UI 状态容器，不会自动把单次查询变为 Room 订阅：前者保存成功后按既有机制刷新，后者观察 Room 变化，避免维护重复缓存。

表单提交时捕获输入与所属用户；Repository 负责转换和 DAO 调用，Composable 收集状态并发送事件。写入失败要保留草稿并显示可重试错误，不能先清空、导航或提示已保存。Room suspend DAO 自身安排数据库执行；`viewModelScope.launch` 不会自动把其它阻塞代码切到后台。

按产品定义账号、项目或工作区的访问范围，读写都使用对应限定；全本地单用户数据不强加账号字段。已授权的管理聚合查询按其范围处理，异步结果不覆盖已切换的作用域。取消异常继续传播，不把取消当成普通失败。

联网缓存还需区分数据库记录 ID、远端 ID、刷新和过期策略。离线编辑按业务契约处理待同步状态与冲突，不将本地插入成功等同远端已保存。

## 带日期的状态

保存业务值和归属日期，按明确时区的当前日判断有效性。每日任务勾选可在日期不匹配时解释为未完成，无需删除任务；只保存当天最新状态时，不能宣称具有完整执行历史。

区分重新读取时的逻辑重置与跨午夜持续显示的自动刷新。若要求前台跨天也更新，要在恢复前台/日期变化时重新计算；不要仅依赖 Room 有新写入。乐观更新需处理写入失败与快速连续点击后旧请求覆盖新值。

## 按风险验证

- 导入：首次启动、再次启动、解析失败、事务中断、提交后标志未保存、重复调用及旧用户数据不被覆盖。
- 迁移：旧版本到新版本、既有各类业务数据保留、空库创建与首次导入。
- 读写：A/B 用户隔离、保存失败不丢表单、成功后列表与派生状态更新、晚到请求与取消。
- 每日状态：同日重启、跨日重开、前台跨午夜（如要求）、时区边界及计数一致。

交付区分源码检查、编译、迁移测试和设备行为验证。涉及导入重试、缓存或迁移时读取 [导入与迁移场景](references/seed-and-migration.md)，不将示例表名与版本作为目标项目默认值。
