# Android 性能诊断与优化证据

## 先区分要录制还是分析

读取用户描述的问题与现有 trace、日志、benchmark 或 APK。已有证据足以定位时先分析，不为了流程重新录制。没有数据时明确要复现的动作、设备/系统、模块/变体、数据规模和测量目标。

优先定义可观察指标：启动时长、帧耗时/卡顿、主线程阻塞、堆增长、分配、包体或耗电。功能错误、网络不可用和设备安装问题先归到相应失败层，不能统称性能差。

## 建立可比基线

面向用户体验的数值采用接近生产的非 debuggable 构建与合理的 profileable/benchmark 配置；debug 可帮助定位代码，但其耗时不作为生产性能结论。

记录构建、设备、系统、应用数据、冷/热启动定义、运行次数、环境与工具设置。前后使用相同输入和方式，多次采样；温度、后台负载、编译/缓存状态不同则先解释差异，不直接宣布改进。

## 按表现选择证据

| 表现 | 优先检查 |
| --- | --- |
| 冷启动慢 | 启动链路、初始化、主线程工作；已有启动 benchmark/trace |
| 滚动或动画卡顿 | 帧与系统 trace，关联 CPU、布局/绘制、图片加载及 GC |
| ANR/界面卡死 | 对应堆栈、主线程阻塞、锁等待、Binder 或重 IO，不从 ANR 标签猜原因 |
| 内存上涨/OOM | 可复现的操作循环、分配与堆证据、对象持有链和资源释放 |
| 包体大/R8 疑问 | 实际变体 APK/AAB、依赖/资源/keep 规则与可用分析产物 |
| 后台耗电 | 明确时间窗与工作负载、后台任务/唤醒/系统记录，避免一次截图推断持续耗电 |

设备与工具按当前可用能力选择；确认 serial、权限、输出位置及是否会改变应用数据。trace/heap 可能包含敏感内容，留在任务允许的位置，不默认上传外部服务。

## 修改以根因为依据

- 阻塞 IO 或重计算出现在主线程时，按职责与成本安排执行上下文；suspend 函数名不证明其内部不阻塞。
- Compose 分清 composition、layout、draw 的工作和状态读取范围；重组计数是线索，不是掉帧或瓶颈的直接证明。
- 长列表检查稳定记录身份、必要分页、图片尺寸和昂贵循环；小列表不为“性能”机械替换成复杂容器。
- remember/cache 必须有正确输入和失效条件，不通过缓存旧数据换取看似更快；不批量添加/移除稳定性标注或更换集合库。
- Views 同样检查布局、绑定、列表复用与资源释放；不把改成 Compose 当默认性能修复。
- 每次针对可解释原因做小改动，用同一场景比较，保留功能回归检查。

## 构建优化与版本分流

先查 AGP/R8/Compose 与工具实际版本、目标变体及可用任务。存在官方支持的分析任务/产物时按当前契约使用；不存在时可做静态建议，但不能生成虚构的量化评分或自动升级工程。

R8/keep 规则要结合反射、序列化、JNI 与库的 consumer rules 判断；不靠关闭混淆或添加整包 keep 作为最终修复。相关变更需验证优化变体的真实功能，debug 成功不足以证明 release 正确。

Baseline Profile 或新分析插件只在目标、工具链和可验证路径合适时引入，不把它们作为所有小修复的强制前置。

## 报告与停止条件

列出问题、证据、根因或待验证假设、改动及前后可比结果。没有设备/trace 时报告静态发现和建议，不能写成已测量优化；一次测量的波动不算收益。

检查受影响的功能和构建路径，通过后停止扩散；不借性能任务重构所有页面或升级全部依赖。需要具体记录格式时读取 [性能证据与复测模板](references/evidence-report.md)。
